# Local catalogue and registration continuity

The SePay overlay intentionally switched all portals from browser mocks to live APIs. Existing PostgreSQL volumes and booking history remained, but the earlier frontend catalogue had never been imported into transport. This made customer search/location choices look empty. The catalogue import is additive: no database reset or old-booking deletion.

Run `./scripts/restore-local-catalogue.ps1` with the local Docker stack running. It imports four geographic labels (TP. Hồ Chí Minh, Đà Lạt, Đà Nẵng, Hà Nội), twelve directional routes, two vehicle layouts per route and seven future service days, then publishes drafts through the existing operator API. Real transport outbox → RabbitMQ → booking inventory → inventory-ready flow enables selling. Re-running on the same day publishes zero duplicates; running on subsequent days adds schedules for the new horizon. These are fictional Sandbox schedules under the development fixture operator, not actual carrier services.

Verification: 168 sellable trips with booking seat inventories; search TP.HCM → Đà Lạt returns a 34-seat sleeper and 22-seat cabin; authenticated API test held two seats for 504,000 VND and released the hold without creating a booking. Existing 6 paid bookings and the SePay-issued ticket were preserved. An initial set of draft fixture identifiers incompatible with frontend UUID validation was cancelled through the operator API before any bookings; its history is retained and it is not sellable.

Home route cards now use the existing photographic assets and link directly to the selected route's search for tomorrow. Live Explore includes route photos, existing editorial offers and journey guides. These editorial sections do not claim backend payment discounts.

Registration now transitions in place at `/register` to a six-digit email verification form within AuthShell. The server challenge ID and email are stored in tab session storage; neither password nor OTP is persisted. Reload resumes pending verification for thirty minutes; editing retains the in-memory form but drops the obsolete challenge context. Resend replaces the challenge ID and has a sixty-second UI cooldown. Verification parses the actual backend session, saves it, clears pending context and uses the same intended-destination logic as login. The legacy `/verify-email` route redirects into the registration flow instead of requesting a challenge UUID from the user.

Tests cover in-place registration → verification → authenticated destination; old challenge replacement on resend; incorrect-code errors; reload recovery; and edit-form continuity. Existing mock auth tests remain passing. Production email delivery depends on SMTP configuration; the local stack captures development email in Mailpit.
